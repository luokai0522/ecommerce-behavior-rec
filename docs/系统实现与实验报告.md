## 2. 五层架构与实际文件

```
展示层  web/index.html            ECharts 大屏 + 用户查询
服务层  server/app.py             Flask，只读预计算结果
推荐层  spark_jobs/itemcf.py      ItemCF 召回
        spark_jobs/als.py         ALS 召回 + 参数实验

存储层  data/processed/ods/       按 dt 分区的 Parquet
        sql/*.sql                 数据仓库与业务库建表
```

**离线/在线分离**：所有耗时计算在 Spark 批处理中完成，结果落 Parquet；Flask 启动时把推荐与标签载入内存，接口只做字典查找，因此响应时间稳定在毫秒级，不随数据量增长。

## 3. 数据链路

清洗规则（`clean.py`）：

1. 丢弃 `user_id` / `item_id` / `category_id` / `behavior_type` / `timestamp` 任一为空的记录；
2. `behavior_type` 映射为 1 浏览 / 2 收藏 / 3 加购 / 4 下单，非四类的记录丢弃；
3. 过滤 `user_id <= 0`、`item_id <= 0` 的异常值；
4. 时间戳转 `timestamp`，并派生 `dt` 分区字段；
5. 按（用户、商品、品类、行为、时间）五元组去重。

运行结果（天池 UserBehavior 抽样 200 万条）：

```
输入 2,000,000 条 → 有效 1,999,716 条（丢弃 284 条：空值 / 非法行为 / 时间窗外的脏时间戳）
用户 834,536 / 商品 749,817 / 品类 7,079
时间范围 2017-11-24 ~ 2017-12-03
输出：10 个 dt 分区目录，Parquet + Snappy
行为分布：浏览 89.59% / 加购 5.51% / 收藏 2.88% / 下单 2.02%
```

**数据质量问题（必须写进论文）**：原始数据在 2017-12-04 之后仅有 26 条记录，且存在 1905 年、2036 年等
异常时间戳。若不过滤，会产生 88 个 dt 分区，按日期切分时"最后 2 天"落到 2025 年，测试集只剩 2 条。
处理方式：把时间窗限定在 `[2017-11-24, 2017-12-04)`。

## 4. 用户画像

四个维度（维度口径见 `user_profile.py`）：

| 维度 | 口径 | 分布（真实数据 834,534 用户） |
|---|---|---|
| 活跃度 | 行为次数固定阈值：≥5 高 / 3–4 中 / 2 低 / 1 沉默 | 沉默 40.2% / 低活跃 25.5% / 中活跃 22.9% / 高活跃 11.4% |
| 品类偏好 | 加权行为（浏览1/收藏2/加购3/下单4）最多的品类及其占比 | 6,423 个品类，头部品类 3.7% |
| 购买倾向 | （加购 + 下单）/ 总行为 | 低意向 83.8% / 中意向 11.5% / 高意向 4.7% |
| 生命周期 | 首末行为跨度 + 距全局最新日期天数 | 成长期 48.9% / 新用户 43.4% / 成熟期 7.7% |

**为什么活跃度不用分位切分**：真实数据行为次数高度离散（中位数 2、最大 18），`q25=q50=q80=2`，
分位切分会退化成同一档，"沉默"用户被并入高活跃。改用固定阈值后才得到合理的四档分布。

输出为 long 表：`user_id | tag_type | tag_value | weight | dt`，共 3,338,136 条（人均 4.0 个标签），与表 4-6 的设计一致。

## 5. 推荐算法

### 5.1 ItemCF

- 行为加权：浏览 1 / 收藏 2 / 加购 3 / 下单 4，同一用户-商品对取最大权重；
- 相似度：余弦形式 `sim(i,j) = Σ w_ui·w_uj / sqrt(Σ w_ui² · Σ w_uj²)`；
- 只保留共现对 `i < j` 避免重复计算，再对称化；
- 每个商品保留 top-50 近邻；
- 打分：`score(u,j) = Σ_{i∈历史} w_ui · sim(i,j)`，过滤历史已交互商品，取 top-10。

### 5.2 ALS（隐式反馈）

- 把行为权重当作隐式反馈强度，`alpha=10` 放大正反馈；
- `regParam=0.1`、`maxIter=10`、`implicitPrefs=True`；
- 用户/商品先 `dense_rank` 编号，训练后映射回原始 ID；
- 隐因子维度做 10 / 50 / 100 三组实验。

## 6. 离线评测

### 6.1 评测口径（两个算法完全一致，保证可比）

| 项 | 设定 |
|---|---|
| 切分方式 | 按日期切分，前 8 天训练、后 2 天测试（`2017-12-03` 为界） |
| 训练集过滤 | 保留交互 ≥5 次的用户与曝光 ≥10 次的商品；交互 1,720,752 → 43,364，用户 30,008、候选商品 2,669 |
| 正样本 | 测试期的**加购 + 下单**行为，且只保留落在候选商品集合内的部分（1,277 条） |
| 推荐长度 | N = 10 |

**候选集一致性**：推荐器只能产出候选商品集合内的商品，若用全量 68 万商品做评测分母，
命中概率会被稀释到 0（实测 Recall ≡ 0）。因此离线评测的候选集必须与训练/召回时的候选集一致。

指标定义：

- `Recall@N = 命中数 / 该用户测试集正样本数`，对评测用户取平均；
- `NDCG@N = DCG@N / IDCG@N`，`DCG = Σ 1/log2(pos+1)`（仅命中位置计分）；
- `Coverage = 推荐结果去重商品数 / 候选商品总数`。

### 6.2 结果（天池真实数据）

| 算法 | Recall@10 | NDCG@10 | Coverage |
|---|---|---|---|
| 热门榜单（基线） | 0.0016 | 0.0006 | 0.0037 |
| ItemCF | 0.0024 | 0.0018 | 0.9981 |
| ALS rank=10 | 0.0008 | 0.0005 | 0.1263 |
| ALS rank=50 | 0.0039 | 0.0022 | 0.8018 |
| **ALS rank=100** | **0.0047** | **0.0031** | 1.0000 |

参数实验（隐因子维度）：

| 隐因子维度 | 10 | 50 | 100 |
|---|---|---|---|
| Recall@10 | 0.0008 | 0.0039 | **0.0047** |
| NDCG@10 | 0.0005 | 0.0022 | **0.0031** |
| Coverage | 0.1263 | 0.8018 | 1.0000 |

### 6.3 结论

1. **个性化显著优于热门榜**：ItemCF 为基线的 1.5 倍，ALS（rank=100）为基线的 3 倍；
2. **隐因子模型优于邻域模型**：ALS 最优约为 ItemCF 的 2 倍，说明隐式反馈建模比共现相似度更适合稀疏交互；
3. **维度尚未到拐点**：10 → 50 → 100 单调提升，与合成数据上的"50 后回落"不同，说明真实用户偏好更复杂，
   需要更高维度表达；下一步应补跑 rank=200 定位拐点。

### 6.4 评测的局限性（答辩应主动说明）

- 没有线上流量，无法做 A/B 测试，只能离线评测；
- 正样本只取加购与下单，忽略了"浏览但未转化"的弱信号；
- 为保证矩阵可学，过滤了长尾用户与商品（交互量 172 万 → 4.3 万），结论只适用于"活跃用户 × 热门商品"子集；
- 测试期仅 2 天、正样本 1,277 条，指标波动较大；Recall 绝对值低（0.16%–0.47%）是数据集与 Top-10 场景决定的，
  评测重点应放在与基线的相对提升。

## 7. 工程问题与解决（可作为答辩素材）

| 问题 | 现象 | 解决 |
|---|---|---|
| Windows 缺少 winutils | `HADOOP_HOME and hadoop.home.dir are unset` | 放置 Hadoop 3.3.6 的 `winutils.exe`，设置 `HADOOP_HOME` |
| 目录 ACL 禁止 chmod | `ChangeFileModeByMask error (5)` | 输出目录改到用户临时目录，跑完再拷回项目 |
| shuffle 分区过多 | 200 分区 × 9 天 ≈ 1800 个 Parquet 文件，JVM 被拖死 | 本地模式降至 8 分区 |
| 模块命名冲突 | 脚本命名为 `profile.py`，与标准库冲突导致循环导入 | 改名为 `user_profile.py` |
| 大数据集上的共现爆炸 | 用户历史过长时相似度对数量平方增长 | 每用户最多保留 50 个商品参与计算 |
